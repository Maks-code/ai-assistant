# Дизайн: корпоративная доработка AI-ассистента (chat-first)

Дата: 2026-03-18  
Статус: согласовано с заказчиком

## 1) Цель

Перевести текущий MVP в рабочую корпоративную версию:
- сделать интерфейс простым, чистым, удобным и “по-корпоративному”;
- оставить чат центральным сценарием;
- внедрить ролевую модель доступа с безопасностью на backend;
- расширить практический функционал и убрать лишний UI-шум.

## 2) Область изменений

- Frontend: реструктуризация layout, упрощение форм и вкладок, ролевой показ разделов.
- Backend: RBAC-конфиг, вычисление эффективной роли пользователя, permission-check на endpoints.
- Product UX: быстрые действия из чата, “мои обращения”, feedback на ответ ассистента, единый паттерн ошибок/пустых состояний.
- Тестирование: API/role-guard/regression и ключевые пользовательские сценарии по ролям.

## 3) Роли и права (RBAC)

### Роли
- `employee`: базовый пользователь.
- `manager`: руководитель блока/функции.
- `kb_admin`: администратор базы знаний.
- `superadmin`: полный доступ.

### Разрешения
- `chat.ask`
- `docs.read`
- `appeals.create`
- `appeals.read_own`
- `appeals.manage`
- `dashboard.read`
- `kb_gaps.read`
- `kb_gaps.manage`
- `profile.read`
- `profile.edit`

### Источник RBAC
- Внешний файл (`RBAC_CONFIG_PATH`) с маппингом `email/group -> role -> permissions`.
- Fallback для аварийного доступа: `SUPERADMIN_EMAILS` в `.env`.
- UI скрывает недоступные разделы, но авторизация всегда проверяется backend-ом.

## 4) Архитектурный контур

### Идентификация пользователя
- Прод-контур: доверенный `X-User-Email` от SSO/шлюза.
- Локальная разработка: fallback на email из профиля.

### Контекст пользователя
- Новый endpoint: `GET /api/me`.
- Возвращает:
  - email;
  - role;
  - permissions;
  - список доступных разделов интерфейса.

### Защита API
- Permission-check для всех маршрутов (особенно manager/admin endpoints).
- При недостатке прав: `403` и понятный `detail`.
- Backward compatibility: существующие endpoints сохраняются, поведение усиливается RBAC-проверками.

## 5) UI/UX (chat-first)

### Принципы
- Минимум визуального шума.
- Простая и предсказуемая навигация.
- Ясные состояния: loading/empty/error/success.

### Разделы по ролям
- `employee`: Чат, Документы, Обращения, Профиль.
- `manager`: + Кабинет блока, Дашборд.
- `kb_admin`: + Админ KB.
- `superadmin`: все разделы + просмотр effective permissions.

### Что убираем
- Избыточные “MVP” подписи и лишние пояснения в каждом блоке.
- Перегруженные формы с второстепенными полями по умолчанию.
- Дублирующие элементы управления.

### Что добавляем
- “Мои обращения” (фильтры и быстрый поиск по своим заявкам/обращениям).
- Быстрое действие из чата: создать обращение по теме ответа.
- Feedback на ответ (`полезно / не полезно`) для контроля качества KB.
- Единый компонент уведомлений и ошибок.

## 6) Потоки данных

1. Пользователь открывает UI -> `GET /api/me` -> фронт строит вкладки и доступные действия.
2. Любой API-вызов проходит через RBAC-check.
3. Для чата: `POST /api/ask` + отображение источников + feedback пользователя.
4. Для обращений: создание/обновление/фильтрация с учетом роли и ownership.
5. Для админского KB: просмотр и обработка fallback-запросов по правам.

## 7) Ошибки и надежность

- `401/403`: четкие сообщения по доступу.
- Защита от “битого” RBAC-конфига:
  - валидация структуры на загрузке;
  - логирование причины;
  - fallback-поведение без падения приложения.
- UI всегда показывает человекочитаемую причину сбоя и путь восстановления.

## 8) Тестирование и приемка

### Автотесты
- RBAC unit/API: разрешенные и запрещенные сценарии по ролям.
- Регресс существующих ключевых endpoint-ов.
- UI smoke: ролевой показ вкладок, базовые action flows.

### Ручные проверки
- Сквозные сценарии для `employee`, `manager`, `kb_admin`, `superadmin`.
- Проверка чата, документов, обращений, дашборда, fallback-панели.

### Критерии готовности
- Роли работают стабильно и проверяются сервером.
- UI упрощен и не перегружен.
- Чат остается основным рабочим сценарием.
- Нет регрессий в текущей бизнес-логике.

## 9) Rollout

- Staging: подключение тестового RBAC-конфига и проверка сценариев по ролям.
- Production: внешний `RBAC_CONFIG_PATH`, trusted identity от SSO/шлюза.
- Пост-запуск: мониторинг `403` и обращений пользователей для корректировки ролей/прав.
